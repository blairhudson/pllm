## Separate execution from data access

Ordinary remote inference exposes prompts and usually token identities,
intermediate activations, attention state, and decoded output to the provider.
Transport encryption protects that data in transit, but the service still decrypts
it to compute.

Private inference changes the execution boundary. A provider performs useful model
work while client data remains encrypted, secret-shared, masked, or confined to
an explicitly trusted environment. Privacy comes from that computation mechanism,
not from changing an API URL or placing another plaintext gateway in front of the
same service.

## Main design families

No single mechanism dominates every model, deployment, and threat model:

| Approach | Execution form | Primary assumptions and tradeoffs |
| --- | --- | --- |
| Fully homomorphic encryption | Compute over ciphertext | Cryptographic protection without a second online party; expensive nonlinear operations, ciphertext expansion, and restricted arithmetic |
| Secure multiparty computation | Compute over secret shares | Efficient operations can be split across parties; requires interaction, preprocessing, and a clear non-collusion or malicious-security model |
| Trusted execution environments | Compute on plaintext inside isolated hardware | Broad model compatibility; relies on hardware, attestation, deployment controls, and resistance to side channels |
| Prepared correlation and masking | Prepare one-time correlated material, then execute on masked values | Moves selected work offline; requires strict one-use material and separation between parties that could reconstruct private values |

Hybrid systems combine these techniques. For example, encrypted or shared linear
layers may be paired with local nonlinear work, secure comparisons, or isolated
execution. Every transition between mechanisms is part of the privacy boundary.

## End-to-end scope

A useful claim states exactly what remains private and from whom. Relevant data can
include:

- prompts, retrieved context, and token identities;
- embeddings and intermediate activations;
- attention and key-value cache state;
- logits, sampled tokens, and decoded output;
- client-specific adapters or confidential model weights.

Protecting only the initial prompt is not end-to-end private inference if later
activations or outputs reveal the same language. Public-weight and
confidential-weight models also require different protocols: hiding client data
does not automatically hide provider weights.

## Trust and leakage

Threat models must distinguish honest-but-curious participants from malicious
ones. They must also state whether parties may collude, whether hardware is trusted,
how keys or preprocessing material are protected, and what happens after replay,
cancellation, or partial failure.

Even when contents remain protected, a service may observe metadata such as timing,
traffic volume, tensor shape, model identity, stage schedule, and approximate
sequence length. Application logging, compromised clients, retained one-time
material, collusion, and side channels can invalidate an otherwise sound arithmetic
protocol. Operational controls and protocol guarantees must be evaluated together.

## Measure the complete system

Private inference moves cost rather than making it disappear. Evaluation should
include client work, preprocessing, provider compute, bandwidth in every direction,
memory, time to first token, steady-state throughput, and failure-related waste.
Measurements should identify cold and warm state and separate offline work from the
online path.

Useful evidence also records the exact model, hardware, protocol parameters, trust
assumptions, and deployment topology. A loopback CPU result does not establish WAN,
GPU, energy, price, quality, adversarial-security, or production-collusion results.
