Use the headless runner for repeatable local measurements:

```bash
pllm benchmark run --prompt-file prompt.txt --max-output-tokens 24 --repetitions 3 --output benchmark.json
```

The report contains sanitized diagnostic measurements. It is not a canonical
research `EvidenceReport`, and a loopback run does not establish WAN, multi-host,
energy, price, quality, or production non-collusion claims.

## Enforce consumer Internet rates

`--backend native --wan` caps every party's TCP streams, including the
client, at **100 Mbps down / 40 Mbps up**. Upload and download are shared across
all that party's peers; they are not per-connection allowances. Override with
`--wan-download-mbps`, `--wan-upload-mbps`, repeatable `--wan-party ID:DOWN:UP`,
or `--wan-profile`. Supplying those options also enables enforcement.

```bash
pllm benchmark run --tiny --backend native --wan --isolate-candidates --warmups 0 --repetitions 1 \
  --max-output-tokens 4 --temperature 0 --inventory-policy request-sized \
  --output wan-report.json
```

Reports print measured end-to-end, online and decode **tokens/second under the
caps**, alongside separately labeled analytical bandwidth floors. Decode uses
`N-1` outputs over the first-to-last output interval. End-to-end request timing
includes demand preparation; provider startup and warmups are separate.
Use `--wan-estimate` for a projection without throttling. See
[WAN readiness](/sdk/deployment/wan/) for party grouping, kernel evidence and the
bounded real-Qwen throughput check. Rate-only emulation adds no Internet RTT;
optional Docker delay/loss controls are separately configured.

Native relays conserve client and all-link stream bytes, including HTTP/WebSocket
framing. Kernel headers and retransmissions are outside that counter. Explicit
`--backend docker --wan` uses kernel queues instead. `--isolate-candidates` gives
each Experiment a fresh client while preserving one shared private comparison
salt, so client memory peaks are comparable. Reports also sample the total live
client/provider RSS in one window. [Full definitions](/sdk/deployment/wan/).

## Account for preparation and delivery

For the public prepared graph, the report's `topology_accounting` includes
separate **startup inventory/bundle** and per-run serialized protocol-body
bytes by directed edge and phase, plus available run-window process CPU seconds
per role. These counters do not measure HTTP/TLS framing, control traffic,
correction acknowledgements, checkpoint distribution before startup, or full aggregate
compute. Missing counters stay `null`; they cannot justify a total-wire-byte
winner or the two-online-server compute cap.

For a cold single-response comparison, `--inventory-policy request-sized`
defers preparation until the token budget is known and issues exactly the
required rows; default `prewarm` issues 64 rows at startup to amortize later
responses. Reports label the policy. Compare startup **plus** run bodies and
cold lifetime CPU, not run-only latency: deferring preparation changes which
window records it. A matched 39+1-token Qwen2.5 cohort saved 23,347,200
covered cold body bytes while online bodies stayed equal. Neither mode measures
full wire bytes or persistent disk use. See the
[prepared protocol guide](/sdk/inference/prepared-protocol/) for exact counters.

The same policies can be bound in an immutable SDK Pipeline using
[`PreparedInventory`](/sdk/components/preparation/inventory-policy/) and
[`ClientBundleTransport`](/sdk/components/protocols/client-bundle-transport/).
Conflicting explicit CLI overrides fail. The report keeps per-run medians separate
from `accounted_setup_through_first_response_body_bytes` and
`total_accounted_benchmark_body_bytes`, which include recorded startup exactly once.

`--bundle-compression zlib` additionally opts into bounded frames for cold
client-bundle transfer. In one matched Qwen2.5 pair it saved 21,076,697 covered
body bytes but increased cold aggregate CPU; warm requests transferred no
bundle. The default is `none`. Reports record the choice, and the
[prepared protocol guide](/sdk/inference/prepared-protocol/) explains the
negotiation, digest verification, and measured tradeoff.

`--prefill-cache-mib` opts into bounded, client-only **exact-prompt** prefill
reuse (0–256 MiB). A warm response with the identical tokens can skip prefill
provider traffic; changed prompts cannot. Use the same token cohort, body
fingerprint and cache warm state when comparing results. With
`--inventory-policy request-sized`, the dashboard sizes preparation before
online execution based on a confirmed cache hit. Its measured Qwen2.5 repeat
saved 97.74 MB in covered bodies; full wire and client peak RAM were not
measured. See `docs/evidence/exact-prefill-cache-qwen25-2026-09-27.json`.

For ordered growing contexts, use `--prompt-sequence-file` with a bounded JSON
array of complete context strings. The same live client executes every context
and `--repetitions` repeats the whole sequence. The comparator matches ordered
per-request token caps, usage and warm states, source locks and sequence digests;
it additionally ranks summed run and setup-inclusive bodies. Reports/archive do
not store context strings. See the [checked SDK sequence example](/sdk/evaluate/benchmark/)
and [client-owned attention placement](/sdk/components/roles/client-linear-roles/).

A checked one-token transport
smoke run uses an explicitly generated tiny checkpoint:

```bash
uv run --frozen pllm benchmark run --tiny --max-output-tokens 1 --repetitions 1 --format json
```

`ClientOnlyCpu`, `TwoOnlineOffsetCpu` and prepared masked linear inference
are all selectable Experiments under this command. The offset option starts
two authenticated worker processes through the same topology supervisor;
the local workers remain co-located and do **not** satisfy the independent
operator privacy condition. Its per-run `topology_accounting` charges each
covered worker setup, online, completion and bundle body once, and records
authenticated CPU samples for all three roles. Headers/TLS, model descriptors,
cold checkpoint distribution, startup CPU, client peak memory and full-response
compute remain outside the reported totals.

Repeat `--experiment` to compare complete experiment configurations. Each
Experiment contains one immutable Pipeline:

```bash
pllm benchmark run \
  --experiment examples/benchmarks/qwen-client-only-cpu-4.yaml \
  --experiment examples/benchmarks/qwen-offset-cpu-4.yaml \
  --experiment examples/benchmarks/qwen-prepared-cpu-1.yaml \
  --experiment examples/benchmarks/qwen-prepared-cpu-4.yaml \
  --prompt "Explain private inference in one sentence." \
  --max-output-tokens 16 \
  --warmups 1 \
  --repetitions 3 \
  --output comparison.json
```

To compare the three W8A8 topologies only, remove
`qwen-prepared-cpu-1.yaml` from the example above. The comparison ranks full
latency, online latency, time to first token, and throughput only when model
fingerprint, input/output token counts, token cap and warm state match. It
does **not** check that all generated token selections match, independently
verify worker operators or establish a total-network winner. Add
`--save-best winner.json` only when selecting the lowest measured loopback
latency for a later diagnostic rerun, not for privacy or production readiness.
Checked candidate and winner files live under `examples/benchmarks/`.
Different numeric options produce different quantized body fingerprints, so the
current transport comparator reports their individual costs without ranking
W4A4 against W8A8.

The same command accepts the client-owned `ClientOnlyCpu` topology. Its
checked-in Experiment uses the same public Qwen checkpoint and W8A8 numeric
settings as the prepared CPU option. Inspect it without loading the checkpoint:

```bash
pllm benchmark run --experiment examples/benchmarks/qwen-client-only-cpu-4.yaml --prompt "Explain private inference in one sentence." --max-output-tokens 16 --repetitions 1 --format json --dry-run
```

Remove `--dry-run` to execute the compiled model locally. Repeating the target
alongside `qwen-prepared-cpu-4.yaml` uses the existing exact body-fingerprint,
token-count and warm-state comparison gates; it does not certify matching
generated selections, cold model distribution or full network/compute costs.
Add `qwen-offset-cpu-4.yaml` to the same command to measure the two-worker
protocol with the identical W8A8 checkpoint and prompt cohort. A checked
generated tiny-checkpoint regression exercises all three Experiments through
this benchmark path with matching body fingerprints and token counts.

## Compare numeric quality

[`pllm benchmark quality`](/cli/reference/benchmark/quality/) compares
Experiment quantization choices against the same pinned float32 reference,
tokenizer and public prompt cohort. To reproduce the two-prompt Qwen3-0.6B
numeric diagnostic (a local copy can be supplied through
`PLLM_REAL_QWEN3_PATH`). In a source checkout, install its optional reference
dependencies with `uv sync --extra quality` before running:

```bash
pllm benchmark quality --experiment examples/benchmarks/qwen3_reference_quality.py:w4a4 --experiment examples/benchmarks/qwen3_reference_quality.py:w8a8 --trust-python --prompts-file examples/benchmarks/reference_prompts.json --top-k 5 --format json
```

The [retained aggregate report](https://github.com/blairhudson/pllm/blob/main/docs/evidence/qwen3-0.6b-reference-quality-2026-09-24.json)
records top-1 agreement of 0/2 for W4A4 and 1/2 for W8A8. No prompt text,
token IDs or logits enter that report. It uses local compiled clear integer
kernels; reference loading is excluded from provider latency, CPU, memory and
network metrics. Neither setting meets a general model-quality gate from
these two prompts. For interpretation and the typed metric, see
[reference agreement](/sdk/evaluate/metrics/reference-agreement/).

The same source-locked two-prompt comparison was also run for
[Qwen2.5-0.5B-Instruct](https://github.com/blairhudson/pllm/blob/main/docs/evidence/qwen2.5-0.5b-reference-quality-2026-09-24.json):

```bash
pllm benchmark quality --experiment examples/benchmarks/qwen2_reference_quality.py:w4a4 --experiment examples/benchmarks/qwen2_reference_quality.py:w8a8 --trust-python --prompts-file examples/benchmarks/reference_prompts.json --top-k 5 --format json
```

It also scored 0/2 W4A4 and 1/2 W8A8, with a larger worst-logit difference
than Qwen3. Each model binds its own checkpoint and reference; do not pool
their scores as one cohort.

An Experiment can instead be built with the SDK in a Python module:

```bash
pllm benchmark run \
  --experiment examples/benchmarks/qwen_prepared.py:cpu_4 \
  --trust-python \
  --prompt "Explain private inference in one sentence." \
  --max-output-tokens 16 \
  --warmups 1 \
  --repetitions 3 \
  --output benchmark.json
```

The `path.py:object` target names one public `Experiment`. `--trust-python` is
required in noninteractive use because resolving the target imports and executes
the local module. Repeat `--experiment` with other objects to compare them.

The same target can configure a provider role:

```bash
pllm serve inference \
  --experiment examples/benchmarks/qwen_prepared.py:cpu_4 \
  --trust-python \
  --host 127.0.0.1 \
  --port 8000
```

The Experiment supplies the model and CPU thread count. Role addresses and
credentials remain `serve` arguments. The example's `prepared_cpu(model,
threads=...)` SDK function accepts another supported model ID, so component
selection does not need to be duplicated for each model.

Use the dashboard when you need a visual transport trace:

```bash
pllm dev dashboard --tiny
```

`--tiny` uses random generated weights and validates transport behavior only.
Interactive runs without `--tiny` use the configured real model.
