The [interactive scorecard and chronology](/research/papers/) connect measured
SDK configurations to their evidence. **SOTA means the highest-performing measured
combination of compatible SDK capabilities for a selected metric, model and workload.**
The search scope and matched comparison determine what the measurements establish.
Original-paper performance is never substituted for a PLLM measurement.

The [complete research data](/research/results/) records every confirmed result,
all 108 exploratory attempts, all 72 measurements and the rejected trials, with
canonical reports and rerunnable Python files. Separate cohorts remain separate.

## Reading the frontier

One line follows each experiment across nine default axes: **request tokens/s,
MB/output token, body-linear compute offloaded, client/aggregate CPU,
client/aggregate memory and client/aggregate network**. Speed and cost axes map
their observed range to 0–100, with the best at 100; lower-cost axes are inverted.
Body offload uses its absolute 0–100% scale. Equal values stay tied, including a
genuine zero, and unmeasured values leave gaps. Every axis is higher-is-better;
positions are not percentages of baseline or a composite score. Actual units
and costs appear in line details and the results table.
Axes are grouped as **Performance → Client → Agg (Aggregate)**, with CPU, memory and
network together within each cost group. Optional provider metrics form their
own group; selections retain this grouping when metrics are added or removed.

### Rewarding offload

**Body offload = 100 × remote body-linear MACs / (client + remote body-linear MACs).**
Counts come from the compiled placement's declared per-row work, with each model
stage counted once. Client-only scores **0%**, the client-owned MLP candidates
**12.31%**, and provider-owned body stages **100%**. Its absolute scale prevents
an all-local cohort from receiving 100 merely because every configuration ties.

This is a plan-derived delegation metric. It excludes attention, nonlinear work
and token lookup/head execution; 100% is not a claim that all client work is gone.
It does not count duplicated worker operations, Preparation arithmetic or setup
overhead as extra useful model work. A provider CPU-time fraction would reward
that extra overhead. Measured client and aggregate CPU seconds show the actual
resource cost alongside delegation. Client-only legitimately uses less CPU in
this small-model cohort because it avoids protocol work, while delegating none
of its decoder body. Cache reuse and public-prefix work avoidance have their own
time and traffic effects; they do not change this per-row ownership fraction.

Client-only and naive two-offset controls have distinct line styles. The naive
offset control uses full input/output shares and sequential CPU execution;
optimized offset finalists are separate lines. The metric picker also exposes
decode throughput, body-only traffic, latency and provider memory. Baseline
controls remain visible when candidate-placement or public-prefix filters change.

Select a line to inspect actual units and its Python configuration. A paper
selection highlights related configurations and links to its chronology card;
cards link back to the chart. Component attribution is labelled separately from
a full-system reproduction. A paper without a matched executable measurement
has no invented performance line.

## Native 100/40 measurement contract

The new frontier cohort uses `--backend native --wan --isolate-candidates`:
each Experiment gets a fresh client process under the same parent-owned private
cohort salt. Native processes run behind opaque TCP relays. Each party shares
one 100 Mbps download and one 40 Mbps upload budget across its concurrent peers,
with a bounded 16 KiB burst. Startup, bundle delivery, preparation push and online
traffic all pass through those budgets. This measures local bandwidth-limited
execution, without an added Internet RTT.

Client and total network count TCP-stream bytes from role startup through the
response, including HTTP/WebSocket framing. Each directed link is counted once;
client network includes both client upload and download, while total adds
provider-peer links. MB/token divides total bytes by authoritative output tokens.
Kernel headers, ACKs, retransmissions, telemetry, upstream checkpoint downloads
and pre-positioned public artifact distribution remain outside this scope.

Client memory is its fresh process's lifetime RSS peak. Total memory is the
largest 50 ms sampled sum of live client and provider RSS, not the sum of their
independent lifetime peaks. Short peaks may be missed; shared pages can be
counted by multiple processes. Process RSS excludes uncharged GPU allocations
and OS cache. Client/total CPU cover benchmark startup through the response and
include the relay/sampler; GPU compute is separate. The idle parent launcher is
outside the measured role graph.

Replay the native frontier after building the public artifacts described below:

```bash
uv run python -m benchmarks.research.confirm .artifacts/research-native-wan.json \
  --native-wan --include-naive-offset \
  --search client=docs/evidence/research-search-client-qwen25-v2.json \
  --search prepared=docs/evidence/research-search-prepared-qwen25-v3.json \
  --search offset=docs/evidence/research-search-offset-qwen25-v3.json \
  --search public_prefix=docs/evidence/research-search-public-prefix-qwen25-v2.json
```

## Measured native 100/40 frontier

All **17 configurations** completed with matching output digests, fresh client
processes and zero observed swap growth. The three baselines and selected
trade-offs are shown below; [research data](/research/results/) contains every
configuration and every metric.

| Configuration | Request tokens/s | Client / total CPU s | Client / total RSS MB | Client / total network MB |
| --- | ---: | ---: | ---: | ---: |
| Client-only CPU baseline | 1.876 | 9.20 / 9.20 | 1,192.76 / 1,192.76 | 0 / 0 |
| Naive offset baseline | 0.0459 | 24.01 / 58.00 | 621.58 / 2,091.27 | 648.43 / 648.43 |
| Prepared baseline | 0.0768 | 21.22 / 64.02 | 605.00 / 2,272.41 | 397.82 / 604.30 |
| Client MLP — delivery | 0.3426 | 26.44 / 43.74 | 1,226.75 / 2,166.31 | 503.71 / 536.34 |
| Prefix + packed | 0.2836 | 14.76 / 36.65 | 543.13 / 1,870.66 | 235.36 / 291.60 |
| Stack + public prefix | 0.1074 | 14.88 / 41.23 | 222.71 / 1,173.62 | 214.15 / 267.76 |

Client-only has the highest observed throughput and zero provider traffic, with
the complete decoder at the client. Moving MLP stages locally also accelerates
the response, but increases client weight delivery and memory. Among candidates
whose body linear stages stay remote, public-prefix packed execution has the
highest observed throughput. The full public-prefix stack instead minimizes
client RSS and offloaded network totals: **63.2% less client RSS**, **48.4% less
sampled total RSS** and **55.7% fewer TCP-stream bytes** than the prepared baseline.
Those two prefix choices reuse 96 explicitly public tokens; the stack additionally
requires 12.25 MB of pre-positioned public artifacts.

These are single-response observations. In this bandwidth-limited cohort,
provider-body Metal does not retain its uncapped latency lead. Local bandwidth
caps, model download exclusions and CPU-versus-GPU accounting remain part of
the comparison, rather than being hidden in a single combined score.

## SDK composition search

[`BeamSearch` and `benchmark_search`](/sdk/evaluate/search/) complement grid and
random search. Bounded beam search measures an incumbent, expands one-axis
neighbors of the measured leaders and retains incompatible, resource-rejected
and failed trials. It does not materialize the full Cartesian grid.

The research [search space](https://github.com/blairhudson/pllm/blob/main/benchmarks/research/combinations.py)
includes CPU thread counts, Metal, preparation scheduling, wire encodings,
delivery and storage, client linear-stage ownership, indexed tokenization and
an explicitly public-prefix cohort. Prepared, two-worker and client-only graphs
are searched separately. Model, numeric and privacy contracts stay fixed within
each adaptive search.

The [research runner](https://github.com/blairhudson/pllm/blob/main/benchmarks/research/search.py)
delegates proposal, admission and execution to the SDK. Every completed
observation retains its exact Python factory. Single-observation adaptive search
is exploratory; a budget-limited winner is the best observed configuration,
not proof of a global optimum.

[Finalist confirmation](https://github.com/blairhudson/pllm/blob/main/benchmarks/research/confirm.py)
uses SDK cohort validation and Pareto ranking to select throughput and byte
leaders. It also selects leaders with provider-owned body linear stages, then
remeasures the distinct finalists with the baseline in one ordinary benchmark
invocation. Its selection manifest binds each factory to the source search and
selection objective. Separate search salts are never merged into one ranked
cohort.

Saved finalist factories honor an explicit `PLLM_RESEARCH_ARTIFACTS` directory
for the published tokenizer and capsule. Their content digests remain required.
Relocating these plan-bound paths changes the configuration digest; a rerun
records the new identity rather than attributing it to the original score.

The chart labels topology, CPU/Metal selection and client linear-stage ownership.
Client-only runs retain the full decoder locally. Prepared and two-worker runs
retain attention and nonlinear operations at the client even when all body
linear stages are remote. The ownership toggle can exclude client-owned body
candidates while retaining the client-only reference; the public-prefix toggle
can exclude that separate workload assumption.

## Historical uncapped SDK-search confirmation

Four bounded searches made **108 attempts and 72 measurements** across the
declared CPU/Metal, placement, transport, preparation and public-prefix choices.
Thirteen selected finalists and three controls were then measured in one fresh
150+8-token cohort. All 16 passed runtime checks and matched output digests.

| Configuration | Full request | Output tokens/s | Covered bodies | Cold aggregate CPU |
| --- | ---: | ---: | ---: | ---: |
| Prepared baseline | 18.91 s | 0.423 | 603.45 MB | 61.47 CPU s |
| Client-only CPU | 7.72 s | 1.036 | Unmeasured setup total | 18.51 CPU s |
| Client MLP — delivery | 9.38 s | 0.853 | 535.68 MB | 35.31 CPU s |
| Prepared — Metal | 15.70 s | 0.509 | 603.45 MB | 34.16 CPU s |
| Two workers — Metal | 16.53 s | 0.484 | 526.34 MB | 35.03 CPU s |
| Prefix + CPU 8T | 11.48 s | 0.697 | 303.57 MB | 40.11 CPU s |
| Existing stack + public prefix | 20.61 s | 0.388 | 266.91 MB | 48.41 CPU s |

Client-only wins observed request throughput, with all computation and weights
at the client. The two client-MLP finalists place **87.69% of declared body linear
MACs** locally. Among provider-owned body configurations without public-prefix
reuse, Metal improves observed throughput **20.4%** over this cohort's baseline.
Allowing 96 public prefix tokens selects a different throughput leader; the
existing public-prefix stack remains the covered-byte leader at **55.8% below
baseline**. The chart includes every finalist, not just this summary.

Each configuration has one observation. Small timing differences do not establish
statistical superiority, and the search budget does not exhaust all combinations.
Request timing excludes pre-run setup. Cold process CPU includes provider startup
but does not measure GPU compute or energy. Client-only online provider bodies
are zero; its unreported setup total is not silently replaced with zero.
Client-only ownership follows its role graph: the historical bundle-storage
sample excludes weights held by its separate local engine.

The original comparison retained a failed aggregate **same-backend** guard while
all individual checks passed. The published
[explicit cross-kernel analysis](https://github.com/blairhudson/pllm/blob/main/docs/evidence/research-finalists-qwen25.comparison.json)
uses the SDK's `--compare-kernels` policy, preserving every original measurement
and binding the original report by SHA-256. Source locks match within each role
graph; model, numeric body, workload and captured outputs match across graphs.
This is a whole-response component comparison, not a CPU-only speedup claim.

## Historical initial Qwen2.5 comparison

The first cohort uses pinned Qwen2.5-0.5B-Instruct, W8A8 with `prefix_f32`,
150 input tokens and eight greedy output tokens. It contains one cold response
per candidate, with cached upstream checkpoints and distinct co-located provider
processes. All generated-output digests match.

| Configuration | Covered bodies | Request latency | Cold aggregate CPU |
| --- | ---: | ---: | ---: |
| Prepared baseline | 603.45 MB | 11.04 s | 37.11 CPU s |
| Exact prepared stack | 476.95 MB | 15.24 s | 37.79 CPU s |
| Stack + 96 public prefix tokens | 266.91 MB | 11.72 s | 27.06 CPU s |

These are distinct objectives: the baseline wins request latency; the exact stack
reduces covered bodies by 21.0%; the public-prefix configuration reduces them by
55.8% for its explicitly public-prefix workload. The public-prefix toggle removes
that assumption from the displayed comparison.

Covered bodies include recorded setup and application-body links, not complete
physical wire, checkpoint downloads or publisher distribution. The indexed
tokenizer adds 9.29 MB of pre-positioned public artifacts; adding the capsule
brings that total to 12.25 MB. The publisher measured 8.03 CPU seconds separately.
Its [publisher report](https://github.com/blairhudson/pllm/blob/main/docs/evidence/research-scorecard-publisher.json)
retains the exact artifact digests and source/body commitments.
Public artifact sizes are not network-transfer measurements.

Client/dashboard process lifetime RSS accumulates across candidates in this
invocation. It cannot rank isolated client peaks. The chart leaves that metric,
full physical wire, representative quality and energy **unmeasured**. Provider
peaks belong to each candidate's fresh role children and remain separately labelled.
Largest provider RSS compares the maximum individual provider peak across role
graphs, requiring a sample from every provider. It is zero for client-only
execution and is not a simultaneous whole-topology peak.
The scorecard preserves N−1 denominators for decode bytes and throughput.

## Python configurations

Every scored row links to a repository Python file and retains its configuration,
Pipeline, source and report digests. These factories create ordinary `Experiment`
objects consumed by the SDK, gateway and benchmark runner:

- [Prepared baseline](https://github.com/blairhudson/pllm/blob/main/benchmarks/research/baseline.py)
- [Exact prepared stack](https://github.com/blairhudson/pllm/blob/main/benchmarks/research/sota.py)
- [Public-prefix stack](https://github.com/blairhudson/pllm/blob/main/benchmarks/research/public_prefix.py)
- [Shared checkpoint and workload contract](https://github.com/blairhudson/pllm/blob/main/benchmarks/research/common.py)

The exact stack combines demand-aware inventory, terminal prefill pruning,
stage-packed requests, row-residue outputs, paged compressed artifact delivery,
paged Preparation and a source-bound indexed tokenizer. The third configuration
adds a trusted publisher's public-prefix capsule and qualified prefix reuse.
All prompt-dependent tokenization and state remain inside the trusted client.

## Rerun the matched cohort

From a built source checkout, publish the public artifacts first. The builder
uses fixed public text and the pinned checkpoint; it does not inspect private
prompts. Its output directory contains the tokenizer index, capsule, public
prompt, canonical Experiment descriptions and a separate publisher report.

```bash
export PLLM_RESEARCH_ARTIFACTS="$PWD/.artifacts/research-scorecard"
uv run python scripts/build_incremental_sdk_experiments.py "$PLLM_RESEARCH_ARTIFACTS"
uv run python -m pllm benchmark run --factory --trust-python \
  --experiment benchmarks.research.baseline:experiment \
  --experiment benchmarks.research.sota:experiment \
  --experiment benchmarks.research.public_prefix:experiment \
  --prompt-file "$PLLM_RESEARCH_ARTIFACTS/prompt.txt" \
  --max-output-tokens 8 --warmups 0 --repetitions 1 --temperature 0 \
  --capture-output-digest --backend native --timeout 900 \
  --output .artifacts/research-scorecard-rerun.json
```

Use one invocation for all compared candidates. Each invocation has a fresh
private cohort salt; separate runs cannot be retrospectively combined as a
matched prompt cohort. For timing uncertainty, collect a new repeated cohort
with its own documented lifecycle policy rather than treating this sample as a
confidence interval. Memory admission and host-pressure checks remain active.

The [canonical first report](https://github.com/blairhudson/pllm/blob/main/docs/evidence/research-scorecard-qwen25.json)
is retained rather than overwritten by the command above.

### Rerun the SDK-selected finalists

After building the same public artifacts, this command replays the saved search
selection, verifies each immutable Python factory and runs all sixteen choices
under one new private salt:

```bash
uv run python -m benchmarks.research.confirm .artifacts/research-finalists-rerun.json \
  --search client=docs/evidence/research-search-client-qwen25-v2.json \
  --search prepared=docs/evidence/research-search-prepared-qwen25-v3.json \
  --search offset=docs/evidence/research-search-offset-qwen25-v3.json \
  --search public_prefix=docs/evidence/research-search-public-prefix-qwen25-v2.json
```

The runner explicitly selects cross-kernel comparison. Its `--recompare` option
instead validates an existing report against those factories and writes a separate
`.comparison.json`; it does not run inference or change the original observations.
Saved search trials live under `benchmarks/research/trials/`; final scored factories
live under `benchmarks/research/finalists/`. Rejected trials remain in each search
report with reasons. The four searches used budgets of 4 client-only, 48 prepared,
24 two-worker and 32 public-prefix trials. All targeted full-request throughput;
byte leaders were additionally selected from their measured observations.

## Paper reimplementation coverage

The chronology's **Hide unimplemented papers** filter includes scoped SDK
adaptations, component references, structural transformations and attack
regressions. Each card specifies its actual coverage and links to native code,
tests and available evidence. An imported planned class or a related citation
alone does not count as implemented work.

- **Slalom:** the prepared Freivalds adaptation now has a
  [Qwen Python configuration](https://github.com/blairhudson/pllm/blob/main/benchmarks/research/slalom_qwen.py)
  and a [composed variant](https://github.com/blairhudson/pllm/blob/main/benchmarks/research/slalom_qwen_composed.py).
  One native 100/40 response at 50+8 tokens measures **140.95 → 130.69 s**,
  **374.00 → 334.21 MB** TCP-stream traffic and **624.02 → 345.18 MB** client RSS.
  Aggregate CPU increases **76.61 → 78.95 s**. Both verify every remote stage
  under the same 40-bit attempt bound and produce matching outputs. The chart
  ranks this same-verifier pair separately from unverified controls. Auditing
  actual native projection counts and memory owners corrected the prior admission
  overestimate; it did not change the protocol. The original TEE construction
  is not reproduced.
- **SIGMA / FuseFSS:** a matched native
  [helper configuration](https://github.com/blairhudson/pllm/blob/main/benchmarks/research/interval_rescale_reference.py)
  compares exact signed rescaling and the original-input nonnegative predicate.
  Universal interval keys from **FSS for Mixed-Mode Secure Computation** reuse
  one compact DCF per width within a one-use helper. All **7,680** checked outputs
  match integer oracles. For fused 16-bit/seven-bit-shift ties-even helpers,
  per-party/lane keys fall **1,718 → 758 bytes** and issuance
  **12.83 → 5.74 ms** per 64 lanes. Online work barely changes,
  **11.30 → 11.03 ms**, and peer bodies stay **668 bytes**. Unfused shared-key
  helpers take **8.89 ms**, **620 key bytes** and **1,336 peer bytes**: fusion
  still trades material/CPU for a round. Hypothetical Qwen 39+8 geometry needs
  **6.66 / 8.14 GB** of unfused/fused keys before other decoder work. The earlier
  prefix-only and independent-compact cohorts stay retained.
  [Source contracts and full costs](https://github.com/blairhudson/pllm/blob/main/docs/research/interval-rescale-reference.md)
  remain component evidence; no decoder score or executable planned API follows.
- **Curl:** a new native reference executes one-use, party-local shared lookup
  from Fig. 4 and public Haar compression. It checks all 512 encoded SiLU rows.
  Four Haar levels reduce dealer-share payload from 4,100 to 260 bytes per
  lookup, while header-inclusive peer frames stay at 136 bytes and maximum
  encoded-domain absolute error rises to 0.12888. The already-truncated input
  boundary excludes protected truncation and whole-decoder costs.
- **SmoothQuant:** a [fixed public Qwen calibration](https://github.com/blairhudson/pllm/blob/main/benchmarks/research/fit_smoothquant.py)
  and [ordinary Experiment](https://github.com/blairhudson/pllm/blob/main/benchmarks/research/smoothquant_qwen.py)
  test the existing channel-equalization adaptation. Twelve held-out prefill
  prompts give **11/12 → 10/12** top-token agreement, unchanged 0.8833 top-5
  recall, and **3.6207 → 2.5092** worst absolute logit error. This mixed result
  is not a quality win. Its changed numeric body cannot share an exact-performance
  ranking with plain W8A8. Offline profile costs and quality evidence appear in
  [Research data](/research/results/).
  A separate native 100/40 pair compares that fixed equalized body with exact
  SDK composition: **78.26 → 70.24 s**, **289.41 → 251.25 MB** TCP-stream traffic
  and **540.85 → 262.96 MB** client RSS. Aggregate CPU increases **34.47 → 37.28 s**.
  The 0.72953 MB profile is pre-positioned; its offline build costs **15.78 CPU s**
  separately. Matching output text on this cost prompt does not erase the held-out
  quality regression. These paper controls are baseline/composition pairs,
  not exhaustive searches of verified or equalized configurations.

The native Curl measurement also compares local two-party execution with a clear
table lookup. Its Python configuration runs the bounded native example:

```bash
uv run python -m benchmarks.research.curl_reference .artifacts/curl-reference.json
cargo test -p pllm-garble --lib shared_lut_reference
```

The dealer is confined to this local research reference. One-use party state
burns on use and malformed input; peer frames bind the public table and issuance.
This is a component reimplementation, not a reviewed transport or an executable
Qwen Pipeline. See the [Curl record](/research/papers/curl/).

## Extending the scorecard

The next SDK reimplementation queue prioritizes **Maverick (2026)** and
**FuseFSS (2026)**, using **SIGMA (2024)** for the latter's unfused comparison,
then **MPCache (2025)** and tensor-scale Curl/Compact/LogRow. Existing SmoothQuant
and Slalom adaptations supply the first paper-specific control cohorts. This
order combines recency, published system coverage and reusable dependencies;
it is not a citation-count ranking. The
[paper-to-SDK delivery plan](https://github.com/blairhudson/pllm/blob/main/docs/plans/paper-sdk.md)
records exact promotion gates and the comparative-study protocol.
Maverick's reference still needs field-specific security justification and a
viable preprocessing-storage design. SIGMA/FuseFSS's compact helper pair still
needs independent review and lower complete-operator costs before tensor and
transport admission.

Add a Python factory and a canonical matched report, then register the cohort in
`docs/data/research/benchmark-cohorts.json`. The docs generator validates source,
quantized body, prompt, output identity, workload, sampling, backend and network
conditions before exposing rankings. Missing metrics remain null and ties survive.
`docs/data/research/implementations.json` separately records paper coverage.

The model selector currently exposes only Qwen2.5-0.5B. Qwen3-4B is next;
its earlier isolated memory results do not substitute for a matched scorecard.
