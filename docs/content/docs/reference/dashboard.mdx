## Launch a real public-model run

```bash
pllm benchmark dashboard
```

The command binds a local dashboard to `127.0.0.1:8791`, opens a browser, and uses
`Qwen/Qwen2.5-0.5B-Instruct` by default. The first launch may download that public
checkpoint. Supply a pinned local snapshot or another supported public model with:

```bash
pllm benchmark dashboard \
  --model /path/to/Qwen2.5-0.5B-Instruct \
  --model-id Qwen/Qwen2.5-0.5B-Instruct
```

Use `--no-open` when the CLI should not launch a browser. The dashboard refuses a
non-loopback bind because its UI accepts plaintext prompts. It validates loopback
Host and browser Origin values and authenticates OTLP ingestion, but it is still a
local harness rather than a remotely hosted application with user login.

## What runs

The dashboard process creates temporary credentials and starts real
`pllm serve` and `pllm preparation serve` subprocesses on free loopback ports. The
dashboard process itself owns the real PLLM client. All three roles export metrics
and traces over loopback OTLP to the dashboard collector.

Startup waits for both model services, prepares a complete inventory, and reaches
`READY` before enabling chat. Real-model runs use a 64-row minimum inventory; a
specific prompt can trigger a larger offline inventory before its online clock
starts. Completed runs retain unreserved rows and do not eagerly refill when the
next exact requirement fits.

Temporary service state and logs are removed when the dashboard exits. Existing
model caches outside its temporary directory may still be reused by checkpoint
resolution.

## Persisted comparison history

Completed and failed run summaries are appended to a local SQLite database. The
default is `$XDG_STATE_HOME/pllm/benchmark-history.sqlite3`, falling back to
`~/.local/state/pllm/benchmark-history.sqlite3`. Choose another path or disable
disk persistence for one session:

```bash
pllm benchmark dashboard --history-db ./results/local-runs.sqlite3
pllm benchmark dashboard --history-db :memory:
```

The state directory requests mode `0700` and the database requests `0600` where
supported. Schema-versioned records are insert-only; database triggers reject
replacement, updates, and deletes. Back up or remove the database deliberately rather than
editing individual records.

Persisted records include model identity/fingerprint, cold/warm session label,
actual context and output counts when available, phase timestamps, inventory
generated/reused/consumed/burned counts, privacy-counter deltas, per-role CPU
deltas and sampled RSS peaks, and a failure type. They do not contain prompt text,
output text, response/session/inventory IDs, endpoint URLs, process IDs, or raw
trace spans.

The comparison matrix and chart use only completed records and group them by model,
model-body fingerprint, cold/warm label, and actual context token count. Failed
records remain inspectable but do not enter medians. The local `/api/runs`
endpoints use bounded keyset pages and share the dashboard's loopback Host/Origin
boundary. The browser loads every page for comparison but expands only the newest
200 records into run-table rows.

## Read the panels

| Display | Meaning |
| --- | --- |
| Role CPU time and memory | Live totals; persisted detail uses per-run CPU delta and sampled RSS peak. Missing process samples remain `n/a`, never zero |
| Sent and received | Custom PLLM application-payload byte counters by role edge |
| Inventory | Current capacity, available, reserved, consumed, and burned rows |
| Total time | Accepted submission through `response.completed`, using a monotonic clock |
| Preparation time | Per-run inventory check/refill; may be near zero when rows are reused |
| Transition | Bounded OTLP settlement interval between preparation and online start; explicit harness overhead |
| TTFT | Online start to first emitted text token; offline preparation is excluded |
| Tokens/s | Authoritative output tokens after the first, divided by first-to-last text-delta time; fewer than two tokens report `n/a` |
| Live network | Bounded retained sequence of current prepared-stage operation spans and attributed payload bytes |
| Preparation online operations | Client audit delta while response is online; expected zero |

Protocol bytes include PLLM payloads/envelopes but not every HTTP, WebSocket, TLS,
or IP framing byte. Process CPU deltas can include runtime and telemetry overhead;
RSS peak is limited by OTEL sampling cadence.
Persisted Client I/O comes from direct signed-envelope audit counters rather than
delayed OTLP samples. Operation counts are stage-level protocol operations, not
generated-token counts or HTTP-request counts.

The first submitted run is labeled `cold` and later submissions `warm` within that
dashboard process. Services, checkpoint loading, and initial minimum inventory are
already READY before any submission, so this label does **not** mean a full process
or model cold start. Total run time begins at submission and includes any
additional per-run preparation, the explicit transition interval, and online
inference. The dashboard is
instrumentation, not a controlled benchmark harness by itself.

Prompts and activation payloads are not attached to OTEL attributes. They still
exist in the browser and trusted dashboard/client process, so browser extensions,
screen capture, local logs, and host compromise remain outside protocol privacy.

## Tiny transport smoke

```bash
pllm benchmark dashboard --tiny
```

`--tiny` generates a one-layer random checkpoint locally and prepares 256 rows. It
is useful for checking role startup, inventory, one-way correction push, online
client/inference traffic, and dashboard rendering. Its output is not meaningful
language, and its timing or memory is not evidence for a real checkpoint.

## Qualify results

Record source revision, exact model revision, process-session label, external model
cache state, inventory state, prompt/output lengths, hardware, OS, Python/Rust
versions, history schema, and command flags.
Do not compare dashboard generation rate with historical BFV preparation numbers,
synthetic matrix kernels, or model-scale projections as if they measured the same
thing.

The dashboard demonstrates protocol behavior from one local run. It does not
establish wide-area performance, model quality, secure erasure, operator
non-collusion, malicious security, or production readiness.

## Troubleshoot startup

- Port 8791 must be free; use `--port` for another loopback port.
- A remote model requires network access and any needed Hugging Face credentials.
- Service startup can take up to five minutes before the dashboard reports an
  error; inspect the displayed startup message and CLI process output.
- Large checkpoints need enough RAM for source and compiled matrices in both
  service processes plus public boundary weights in the client.
- Use `--tiny --history-db :memory: --no-open` first when validating packaging or
  a headless host without retaining records.
