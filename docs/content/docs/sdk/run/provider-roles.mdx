---
title: "Provider roles"
description: "Understand the responsibilities of deployment operators, preparation services, and inference services."
---

Provider supplies static component metadata and implementation artifacts. Operator supplies process placement, authenticated identity, authorization, storage, and operational policy. Preparation creates or installs method-specific material. Inference consumes assigned plan work. A deployment may combine processes, but cannot erase semantic role boundaries or establish non-collusion.

Metadata discovery through `pllm components` never loads providers or native libraries. Research discovery never executes recipes. `pllm serve inference` and `pllm serve preparation` start the two roles, but authenticated role-plan delivery and a complete target lifecycle contract remain blockers. See the [serving guide](/learn/integrations/local-gateway/).

## Python SDK example

```python
from pllm.components import get, get_component
from pllm.roles import Inference

role_class = get("pllm/inference")
method = get_component("pllm/masked-linear")
assert role_class is Inference
assert role_class.describe().role_eligibility == ("inference",)
assert method.role_eligibility == ("client", "preparation", "inference")
```

API: [`pllm.components.get` and `get_component`](/sdk/reference/python/pllm/#objects-and-signatures)

Role metadata does not establish operator identity, authentication, or non-collusion.

For untied public checkpoints, `pllm.roles.OutputHeadAtInference` is a
digest-bound `boundary` placement option in the prepared-role Experiment.
It moves the output-head matrix from the trusted-client bundle to Inference,
without moving token lookup or changing the plaintext trust boundary.
See [network I/O experiments](/sdk/evaluate/benchmark/) for its cold/online
cost tradeoff and the SDK example.
`pllm.roles.ClientPrefixLayers` separately assigns a bounded complete prefix
of decoder layers to the trusted client. It keeps the remote suffix prepared
and masked, but adds prefix matrices to the client bundle; inspect its matched
[cold versus online results](/sdk/evaluate/benchmark/) before selection.

## Coupled private vocabulary boundary

`PrivateLookupAndFullHead` with `PreparedBoundaryRoles` assigns a tied W8A8
token table and its complete output head to two online boundary workers. The
prepared body keeps its existing Inference and offline Preparation roles. The
client keeps tokenizer queries, decoder state, reconstruction, full logits and
sampling local, and receives no tied vocabulary matrix.

```python
from pllm import Deployment, ExecutionBudget, Experiment, Model
from pllm.profiles import MaskedLinearCpu
from pllm.roles import PreparedBoundaryRoles, PrivateLookupAndFullHead

experiment = Experiment(
    "private-boundary",
    MaskedLinearCpu(
        Model.tiny(),
        boundary=PrivateLookupAndFullHead(),
        topology=PreparedBoundaryRoles(),
    ),
    Deployment.local(root=".pllm/private-boundary"),
    ExecutionBudget(requests=1, max_input_tokens=256, max_new_tokens=8),
)
```

`examples/private_boundary.py` executes this composition through `serve_local`
and the ordinary SDK, including paged artifacts, packed/residue body frames and
demand preparation. Local native execution and shared TCP rate caps are supported.
Network planning, Docker, untied or auxiliary token tables, Metal, verification,
retained state, prefix caches, epoch schedules and MLP tiling reject this initial
composition.

The two boundary workers must not collude; Preparation's existing erasure and
non-collusion requirements also remain. Co-located child processes establish
functionality, not independent operators or cryptographic review. Cold-client
costs depend on whether workers already own the public source. Full-head replies
and every executed generated-token lookup remain charged; embedding-only lookup
cannot remove a tied client head.

Contract, accounting and replay:
[coupled private boundary](https://github.com/blairhudson/pllm/blob/main/docs/research/private-boundary-sdk-reference.md).
