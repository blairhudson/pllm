title: "Freivalds stage verification"
description: "Check prepared public-weight stage outputs with authenticated one-use client projections."
---

[`FreivaldsVerify`](/sdk/reference/python/pllm/verification/#freivaldsverify)
(`pllm/freivalds-verify/v1`) is constructed, serialized, and accepted by
`VerifiedMaskedLinearCpu` in the verification slot. Trusted Preparation authenticates
projections for a bounded session attempt budget; the client verifies claimed
integer stage results before dequantization and burns used material. A distinct
verified executor now binds the [compiled decoder](/sdk/inference/verified-masked-linear/)
to those one-use rows; a bare remote callback cannot claim verified execution.
The optional `PreparedProviderRoles` topology selects separate local role children
through the ordinary SDK, gateway and benchmark command. A complete static
schedule does not itself prove verification: runtime admission checks the actual
prepared verifier inventory. It cannot stop colluding or malicious Preparation;
there is no whole-deployment cryptographic proof.

## Python SDK example

```python
from pllm import Deployment, ExecutionBudget, Experiment
from pllm.profiles import VerifiedMaskedLinearCpu
from pllm.roles import PreparedProviderRoles
from pllm.sources import TinyModel
from pllm.verification import FreivaldsVerify

experiment = Experiment(
    name="freivalds-guide",
    pipeline=VerifiedMaskedLinearCpu(
        TinyModel(model_id="freivalds-guide-tiny"),
        verification=FreivaldsVerify(target_failure_bits=48),
        topology=PreparedProviderRoles(),
    ),
    deployment=Deployment.local(root="local://freivalds-guide"),
    budget=ExecutionBudget(requests=1, max_input_tokens=64, max_new_tokens=1),
)
resolved = experiment.resolve()
assert resolved.verification_target_failure_bits == 48
assert resolved.requires_preparation
assert len(resolved.role_graph.roles) == 3
```

Save as `experiment.py`; [install the base package](/learn/installation/) and run
`pllm gateway --local --experiment experiment.py:experiment --trust-python`.
For a comparable checkpoint-bound diagnostic, use
`pllm benchmark run --experiment examples/benchmarks/qwen_prepared.py:verified_cpu_1 --trust-python --max-output-tokens 16`
alongside `cpu_1` or a client-owned experiment on the same checkpoint and token
cohort. The benchmark records covered offline and online serialized bodies and
available per-role CPU from process birth through the first cold response, but
not full wire cost or accelerator work. In a matched Qwen2.5-0.5B CPU-only
[cold diagnostic](https://github.com/blairhudson/pllm/blob/main/docs/evidence/slalom-prepared-topologies-cold-cpu-2026-09-26.json),
this verifier used **142.83 s** aggregate CPU against **28.65 s** for the
two-worker offset comparator; Preparation alone used **109.87 s**. It fails
the measured cold CPU objective on this one response. Tiny weights test the
protocol, not model quality.

API: [`FreivaldsVerify`](/sdk/reference/python/pllm/verification/#objects-and-signatures)

<Callout type="info" title="Research citation">

[Slalom](/research/papers/slalom/) motivates client verification of delegated
linear work. PLLM uses authenticated projections with trusted offline Preparation
and a different non-collusion boundary; this is not a TEE reproduction. Its
current benchmark evidence does not establish Slalom's system-level claims.
The paper's attested-enclave-plus-untrusted-accelerator placement remains a
distinct pending topology requiring real attestation, protected key release and
enclave-local nonlinear/KV execution before it can run.

</Callout>
