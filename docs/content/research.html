Private inference,
measured.

Use outside compute. Keep sensitive context local. Private inference must protect the prompt without turning the user's device into the model server. PLLM studies how to make that useful: a small client, affordable Preparation, responsive generation and less data moved.

01 / THE PROBLEM

Remote compute.
Private context.
A practical client.

Ordinary APIs reveal the prompt to the provider. Local models keep it on the device but require local weights, memory and compute. Private inference must delegate useful work while protecting the prompt, intermediate activations and outputs under a stated trust model.

In PLLM's prepared topology, the client keeps plaintext and model state; Preparation supplies fresh one-use corrections; Inference calculates on masked inputs. Preparation must follow the protocol, erase masks and not collude with Inference. Every boundary adds work, storage or communication.

02 / EIGHT RESEARCH OBJECTIVES

Progress in one.
Pressure on another.

Each objective is a research problem. Smaller memory can mean more CPU or network exchanges. Batching can save work but increase waiting and RAM. Reuse can lower traffic while retaining more private state. The useful frontier depends on the device, workload and links.

Quality, correctness and the privacy contract constrain every comparison. We measure tradeoffs rather than collapse them into one universal winner.

01 / LOWER MB

Client memory

How small can the complete client become while substantial model compute stays remote? Paging and tiling trade memory for I/O, work or exchanges.

02 / LOWER CPU SECONDS

Client CPU

How little work must the device do to use outside compute? Compression and private boundaries can consume the capacity that offloading frees.

03 / LOWER CPU SECONDS

Preparation CPU

How cheaply can fresh material be issued? Batching can save work; preparing for unused output tokens wastes it.

04 / LOWER MB

Preparation memory

Can Preparation fit on hardware the user controls? More parallel issuance can improve speed while increasing live masks, corrections and workspace.

05 / LOWER SECONDS

Time to first token

How quickly does the user see an answer? Loading, preparation, queueing, prefill and dependent round trips can all delay the first output.

06 / HIGHER TOKENS PER SECOND

Decode throughput

Can generation stay fast after the first token? On-demand material reduces waste but can introduce pauses between tokens.

07 / LOWER BASE MB

Base all-link traffic

How little data must move for setup, public delivery and a stated prompt's prefill? Warm reuse can lower this base while adding retained storage.

08 / LOWER MB PER OUTPUT TOKEN

Per-token all-link traffic

How little communication does generation add? Count every link and output-related preparation, including prepaid material burned unused.
